## P0：一周内做完，先让系统"可验证、可回滚、数据可信"

### P0-1 备份与重复副本出仓（.git 与 .gitignore 已就位，只差清场）

现状：根目录已有 `.git` 和一份质量不错的 `.gitignore`（`backup_*/`、`.venv/`、`dist/`、`*.db` 都已忽略）。所以缺的不是配置，是**工作区里还躺着几份完整副本**，检索和 ide 索引都会被污染。

动作：

1. `git status --ignored` 确认这些目录确实被忽略，没有误跟踪。
2. 把 `backup_20261123_1219`、`backup_before_rbac`、`_verify_tmp`、`mes-framework`（另一份完整工程）、`backend\.venv\.*` 里的垃圾移到**项目目录之外**（例如 `D:\mes-archive\20261127\`），不要直接删——里面有 RBAC 改造前的对照代码。
3. 清完做一次冷启动验证：删掉一个无关紧要的缓存后 `启动.bat` 仍能跑起来，说明没有代码依赖被误移。

验收：`git status` 干净；目录里只剩一份 `backend`、一份 `frontend`；项目根体积降到百 MB 级。

### P0-2 主链路回归测试（已交付，需接进日常）

动作：

1. 按上面的跑法先跑通一次，确认 7 条全绿。
2. 在 `docs/README.md` 的验证记录里加一行「pytest 主链路 7 项通过」。
3. 定一条规矩：**动 `main.py` 里的状态机、动 `models.py` 的字段，必须先跑这组测试**。现在这些规则全靠人脑记，是最大的回归风险点。

验收：`pytest tests -q` 一条命令给出通过/失败的确定结论，不依赖手工点页面。

### P0-3 时间口径统一（班次与日报的地基）

现状：`models.py` 里全是 `datetime.utcnow`（naive），`pack` 里 `closed_at=datetime.utcnow()`，而 MES 的班次、日报、良率统计都要按本地时间切日。

动作（选一种并写死，推荐 A）：

- **A（低风险）**：全库统一"UTC naive"，新增 `backend/app/timeutil.py` 提供 `utc_now()`，把散落的 `datetime.utcnow()` 全部替换为它；只在 API 出参和前端展示时转 UTC+8。
- B（彻底但改动大）：`DateTime(timezone=True)` + aware datetime。注意 SQLite 对带时区的时间支持不完整，落库仍会退化成字符串，收益有限，不建议现在做。

验收：全项目搜不到裸 `datetime.utcnow`；同一台设备过站记录跨零点时，日报里能正确落到前一天。

### P0-4 初始口令不能是明文

现状：`seed()` 里 `Account(username="admin", password="123456")`，`models.py` 的列注释还写着"V1 演示用明文"，README 也把 `admin/123456` 写成了登录说明。

动作：

1. `seed()` 改为 `password=auth.hash_password("123456")`（`auth.needs_rehash` 已兼容明文，老库不受影响）。
2. 给 `accounts` 加 `pwd_changed_at`（或直接加 `must_change_pwd` 布尔），首次登录返回标记，前端登录成功后强制跳改密页。
3. README 里的默认口令改成「首次启动口令见部署单，登录后必须修改」，口令不再进文档。

验收：新库初始化后 `SELECT password FROM accounts` 是 `pbkdf2_sha256$...` 而不是 `123456`；用未改密的账号访问业务接口被拦或只能进改密页。

## P1：两周内，解决"并发写坏数据"和"模型留坑"

### P1-5 过站写库加乐观锁（现在只有工单有 `rev`，Unit 裸奔）

现状：`WorkOrder` 有 `rev` 但 `station` 接口建完就提交，Unit 没有任何版本控制。两个工位同时提交同一 SN（或重复扫码），会产生两条 pass 记录，前端看板数量虚高。

动作：

1. `units` 加 `rev INTEGER NOT NULL DEFAULT 0`。
2. `station` 提交改写成「读 → 校验 → `UPDATE units SET state=..., current_station=..., rev=rev+1 WHERE id=? AND rev=?`」；`rowcount==0` 就重读重试，最多 3 次，仍失败返回 409「该 SN 正在被其他工位处理，请重试」。
3. 顺带把 `station_records` 的唯一性约束按业务定：如果允许"同一站先 fail 后 pass"，就用 `(unit_id, station, result, created_at)` 不可行，改为**只靠乐观锁 + 应用层幂等**，别加唯一索引（加了会把返修流程锁死）。

验收：并发脚本同时给同一 SN 打 10 次 pass，数据库里 pass 记录 ≤ 2（第一次 + 返修后重测），`unit.rev` 单调递增。

### P1-6 工单站点序列从 JSON 列拆成表

现状：`wos.stations` / `wos.flows` 是 JSON 列，跳站校验靠 `stations.index()` 算下标，改工艺（中间插一站）时历史工单的下标含义会漂移。

动作：

1. 建 `wo_routes(wo_id, seq, station_code, station_name)`，`seq` 从 1 开始，唯一键 `(wo_id, seq)`。
2. 建单时把 `merge_flow_stations()` 的结果写进表；`station` 接口的跳站校验改成「查 `seq < 当前seq` 的站是否都有 pass 记录」，不再依赖 JSON 下标。
3. 老数据用一次性脚本回填（读 `wos.stations` 逐条 insert），回填后 JSON 列保留只读兼容，或直接删列（配合 P2-10 的 Alembic）。

验收：给一张已投产的工单在工艺中心里插入一站，历史工单过站顺序不变；跳站校验仍返回 400。

### P1-7 明确「一 SN 一生一单」还是「SN 可跨单」

现状：`units.sn` 是全局 unique，所以同一个 SN 返修重开单时插不进去，只能走 `replace-sn`；这条规则没写进文档，读代码的人会踩。

动作：二选一，并写进 README 的「业务规则」段。

- 保持「一 SN 一生一单」：在 `import_sns` 的跳过原因里区分「本单已存在」和「其它单已存在」，后者返回明确提示，避免操作员以为是扫码枪问题。
- 放开跨单：改 `UniqueConstraint(sn, wo_id)`，同时把 `/api/query/sn/{sn}` 改成可带 `wo_id` 消歧，前端查询页加一个工单选择。

验收：规则在文档里有原文；导入一个属于别单的 SN，提示语能说清是"已被工单 X 占用"。

### P1-8 数据库备份自动化

现状：`mes.db` 在 `.gitignore` 里，靠人手拷。WAL 模式下直接复制 `.db` 文件可能拷到不一致状态。

动作：

1. 写 `scripts\backup_db.bat`：`sqlite3 mes.db ".backup 'backup\mes_%DATE:~0,4%%DATE:~5,2%%DATE:~8,2%.db'"`，备份后跑 `PRAGMA integrity_check`。
2. 任务计划每天 02:00 执行，保留 30 天，删除前先校验最新备份可打开。
3. 每周挑一份拷到另一台机器或网盘（异地），并每季度做一次真实恢复演练。

验收：连续 7 天有备份文件；随便挑一份能 `sqlite3 x.db "select count(*) from units"` 查出数据。

### P1-9 生产启动方式与开发启动分开

现状：`启动.bat` 是 `uvicorn --reload` + `npm run dev`，这是开发态；车间产线机不该跑 `--reload`（改文件会重启、还可能吃掉正在写的请求）。

动作：

1. 新增 `启动_生产.bat`：`python -m uvicorn app.main:app --host 0.0.0.0 --port 8007 --workers 1`（SQLite 单写者，worker 必须为 1）。
2. 前端先 `npm run build`，用 `frontend/dist` 由后端托管（现在的静态托管已经做好了，含 no-cache 头）。
3. 用 NSSM 或任务计划注册成服务，开机自启、崩溃自拉起。

验收：生产机上改一个 `.py` 文件服务不重启；进程被杀后 1 分钟内自动恢复。

## P2：一个月内，工程化收尾

### P2-10 迁移收敛到 Alembic

现状：`_migrate_sn_replace_columns`、`_migrate_wo_flows_column` 这类手写 `PRAGMA`/`ALTER` 函数会越堆越多，没有版本号，出问题无法回退。

动作：引入 Alembic，把现有 `create_all` + 手写迁移合并成一个基线版本，之后每次改表都出 migration 脚本；启动时不再自动改表，改为部署步骤里 `alembic upgrade head`。

验收：空库 `alembic upgrade head` 一次建全表；`alembic downgrade -1` 能退回上一版。

### P2-11 审计日志防篡改

现状：`audit_logs.detail` 只有 512 字符（过站审计一长就被截断），且可直接 UPDATE；MES 审计是要给客户和审核看的。

动作：`detail` 改 TEXT；加 `prev_hash` / `entry_hash`（`sha256(prev_hash + 关键字段)`）形成哈希链；加一个 `scripts\verify_audit.py` 校验链完整性。

验收：手工改一条历史的 `detail`，校验脚本能定位到断链位置。

### P2-12 收紧 CORS 与令牌存储

现状：`allow_origins` 未配 `MES_CORS_ORIGINS` 时是 `["*"]`；token 存 localStorage，12h TTL，无刷新机制。

动作：生产环境 `MES_CORS_ORIGINS` 显式配成内网域名/IP；上 HTTPS（自签也行）；token 改短 TTL（如 2h）+ 静默刷新，或改 HttpOnly Cookie + CSRF token；`X-Operator` 头只作为显示用，不要参与任何权限判断（现在确实只是展示，保持这个边界）。

验收：不带 `MES_CORS_ORIGINS` 启动时日志里有显式告警；外部域名跨域请求被拒。

### P2-13 车间弱网下的提交可靠性

现状：扫码枪直连 PC，网络抖一下过站就失败，操作员会重复点。

动作：前端加本地待提交队列（localStorage/IndexedDB），每条带 `client_uuid`；后端 `station_records` 加 `client_uuid` 唯一索引，重放天然幂等；前端显示"待同步 N 条"。

验收：断网状态下连续过 5 站，恢复网络后自动补传，且数据库里没有重复记录。

## 收尾建议：先锁一条闭环产线

界面现在 40+ 个视图，功能面已经远超"5 页初版"，但**能端到端跑通并有人负责的产线只有一条才值钱**。建议先把这条链路钉死：

> 建单 → 导 SN → 过站（含不良转维修/返修）→ 装箱 → 出货查询

其余页面（工艺中心、设备、环境监控、产品资料等）在导航上标「原型 / 预留」，避免车间以为都能用。等功能面收敛，再按上面的 P1/P2 逐个补。

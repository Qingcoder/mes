# 第一部分 · 立项

## 1.1 项目定义

| 项 | 内容 |
|---|---|
| 项目名称 | **戴盟 MES 生产管理平台**（内部代号 mes-greenfield） |
| 品牌风格 | 遵循戴盟品牌规范：中国红主色 + D 字母解构 logo（详见 `05_品牌与视觉规范.md`） |
| 项目目的 | 搭建一套 MES 系统，满足戴盟公司的小批量生产要求 |
| 项目性质 | 从零自研，非二次开发、非二次定制 |
| 参照系统 | dm-mes-v106 · 戴盟智造数字化管理平台 V1.0.11 |
| 参照方式 | **仅作需求规格输入，不复用其任何源码** |
| 交付目标 | 一套自主可控、结构清晰、可喂给 AI 持续转化的 MES 代码 + 架构资产 |

**关键原则**：参照系统回答"要做成什么样"，不回答"代码怎么写"。继承它的功能范围，不继承它的技术债（1.89MB 单文件内联、字符串替换式品牌注入）。

## 1.2 商业论证（为何现在做）

**现状问题**（用户口述）：

- 记录混乱
- 没有生产系统

**立项理由**：用一套 MES 系统承接小批量生产记录，建立工单 → 过站 → 包装 → 查询的主线闭环，替代分散混乱的记录方式。

**待补**：价值基线（过去 6–12 个月的追溯耗时、记录差错率等），用于验收对照。

## 1.3 路线决策

**选定：绿场自研（Greenfield）**

| 备选路线 | 未选原因 |
|---|---|
| 接着改本地定制版 | 受制于单文件内联架构，扩展性差，产出对 AI 转化价值低 |
| 绞杀者渐进替换 | 并存期需维护两套同步，复杂度高于本项目承受范围 |

**选择理由**：① 架构从第一天就干净，可演进；② 产出标准化文档与代码，是 AI 转化的合格输入；③ 完全自主可控，无历史实现束缚。

**接受的代价**：放弃快速上线，接受 4–8 周出 V1。

## 1.4 目标（可测）

1. 产出一套可独立部署运行的 MES，覆盖生产主线闭环
2. 沉淀结构化架构资产：需求清单、ER 图、API 契约、架构决策记录
3. 每张架构文档均可直接喂给 AI 转化为下一阶段产物

## 1.5 V1 范围（最低要求 · 主线闭环）

> 以下为**初版方向**，详细规则待用户补充后升级为正式版本。
> 已定方向：SN 导入现成清单 / 站点每工单可配 / V1 纳入单账号登录 / 包装配比自定义 / 手机手动输入。
> 待补充：导入文件格式与校验、站点流转细则、不良原因码体系、配比填写与装箱边界。

### 1.5.1 工单维护 `wo`

| 功能 | 规则 |
|---|---|
| 建工单 | 字段：产品、批次、计划数、产出地点（戴盟公司 / 联想智造） |
| SN 清单 | **导入现成清单**（Excel / TXT），需实现导入功能；SN 格式如 `DAP93226AS00019D` |
| 站点配置 | **每工单可配**：建单时指定该单站点顺序（背包单 / 夹爪单各走各的） |
| 工单状态 | 草稿 → 已下发 → 生产中 → 已完工 → 关闭 |

### 1.5.2 过站作业 `op`

| 功能 | 规则 |
|---|---|
| 过站操作 | **手机手动输入 SN**（扫码枪后续再加）→ 校验当前站点是否在本单序列中且顺序合法 → 判定通过 / 不良 |
| 不良处理 | 选不良原因码；返修后**回到当前站**重测（不回第一站） |
| SN 状态机 | `待过站 → 通过 / 不良 → 返修 → 已过站`；状态流转收敛在服务层，页面只调方法不直接改状态 |

### 1.5.3 包装出库 `pack`

| 功能 | 规则 |
|---|---|
| 配比规则 | **自定义配比**：建单时填写本单装箱配比（N 台/箱），不写死背包+夹爪 |
| 装箱校验 | 所有 SN 必须通过最后一站才允许装箱 |
| 封箱出库 | 手动输入 SN 入箱 → 满配比自动封箱 → 生成箱号 → 出库记录 |

### 1.5.4 数据查询 `query`

| 功能 | 规则 |
|---|---|
| SN 追溯 | 按 SN 查：所属工单、过站记录、不良/返修记录、箱号——追溯闭环，V1 必做 |
| 工单进度 | 按工单查：已过站数 / 剩余数 / 不良数 |
| 箱号查询 | 按箱号查：箱内 SN 清单 / 封箱出库时间 |
| 导出 Excel | **V1.1 延后**，不影响主线 |

### 1.5.5 登录（V1 纳入）

- **单账号 admin 登录**，防止误操作；不做多角色权限（V1.1 再做完整账户体系）
- 登录入口归在**接入层**
- 从原 V1.1 延后项提前至 V1

**V1.1 延后**：完整账户权限 account（多角色）、质量控制 quality、生产报表 report、生产看板 dash、导出 Excel。

## 1.6 不做什么（范围红线）

- 移动端 App / 小程序
- 多工厂 / 多组织架构
- AI 视觉质检
- ERP / 上游系统对接
- 复用参照系统源码

## 1.7 验收标准（可测）

1. **SN 全流程追溯**：一条 SN 从清单导入 → 工单下发 → 过站 → 装箱 → 出库，查询页可完整回溯，各节点状态一致
2. **品牌可配置**：换品牌名 / 主题色只改配置，不改代码，10 分钟内生效
3. **数据安全**：断电重启数据不丢；并发写入不产生覆盖
4. **质量门禁**：资产 / 功能 / 逻辑三道门禁全绿

## 1.8 技术选型方向（候选，待 ADR-001 定稿）

> 视觉层须遵循戴盟品牌规范：中国红主色 + 官方 logo，详见 `05_品牌与视觉规范.md`。

| 层 | 候选 | 说明 |
|---|---|---|
| 接入方式 | **手机浏览器手动输入 + 账号登录** | 扫码枪后续再加；不依赖专用硬件 |
| 前端 | Vue 3 + TypeScript | 组件化，替代单文件内联 |
| 后端 | Python FastAPI | 保留 Python 熟悉度 |
| 数据库 | SQLite 起步 → PostgreSQL | 平滑迁移路径 |
| 同步 | REST + 乐观锁重设计 | 不照搬原 rev 轮询机制 |

## 1.9 资源与约束

- 人力：1 人 + AI 协作
- 周期：4–8 周出 V1
- 纪律：先写规格再写代码；参照物不当事实标准

## 1.10 风险与对策

| 风险 | 对策 |
|---|---|
| 范围蔓延 | 用"不做什么"清单卡住 |
| 把参照系统当事实标准 | 先写规格，再写代码 |
| 一人开发质量风险 | 三道门禁 + 自动化测试 |

# 第二部分 · 调研结论

## 2.1 项目章程八要素（制造业通用）

一页纸章程 = 项目的"宪法"：启动写 1 小时，后期省 100 小时扯皮。

| 序号 | 要素 | 要回答的问题 |
|---|---|---|
| 1 | 项目目的 | 做什么、为什么 |
| 2 | 商业论证 | 为何现在做 |
| 3 | 范围声明 | 含明确排除项 |
| 4 | 成功标准 | 3–5 条可测 |
| 5 | 预算上限 | 授权额度 |
| 6 | 里程碑 | 4–6 个节点 |
| 7 | 风险假设 | 3–5 条 |
| 8 | 签字授权 | 发起人签字方生效 |

**对照我们的立项单**：项目目的、范围声明、成功标准、风险假设已写；**商业论证（部分）、预算上限、里程碑、签字授权待补**。

**最易漏的一项：排除清单**。范围蔓延的典型幅度达 40%（Arcturus Pro 制造业项目观察）。没写进排除清单的，迟早会被当成"当然要做"。我们的 5 条红线已就位。

## 2.2 成熟方案图谱

| 方案类型 | 代表 | 实施周期 | 成本结构 | 适合 |

2024 全球 MES 市场 215 亿美元，2025 预计破 250 亿，CAGR 10.8%。

## 2.4 ISA-95 / MESA-11 · 11 项功能基准

资源配置与状态 / 生产调度 / 调度单元分配 / 文档控制 / 数据采集与获取 / 劳动力管理 / 质量管理 / 维护管理 / 产品跟踪与追溯 / 绩效分析 / 工艺管理。

**我们 V1 覆盖 5 项**：生产调度、调度单元分配、数据采集、质量管理、产品跟踪与追溯。其余留 V1.1。

## 2.5 5 类方案 TCO 与数据主权

| 方案 | 功能深度 | 周期 | 成本结构 | 数据主权 |
|---|---|---|---|---|
| Odoo 开源 MES | 中高 | 2–12 周 | 软件低、服务按需 | 可私有化 |
| 纯开源 MES | 中 | 视团队 | 软件低、人力高 | 强 |
| 商业 MES | 高 | 3–12 月 | 许可+实施高 | 多为 SaaS |
| 自研 | 完全按需 | 6–18 月 | 人力成本高、隐性大 | 完全可控 |
| Excel / 轻工具 | 低 | 几天–几周 | 低 | 弱 |

选型五维：业务匹配 · 三年 TCO · 数据主权 · 实施能力 · 可演进性。

## 2.6 选型决策树

| 条件 | 推荐 |
|---|---|
| 大型集团 + 复杂工艺 + 全球化 | 国际大厂 |
| 大中型 + 国产化 + 行业特性强 | 国内厂商 |
| 中小制造 + 快速上线 + 预算有限 | SaaS / 低代码 |
| 特殊合规（制药 GMP 等） | 专业厂商 |
| **业务独特 + 长期 IT 团队** | **自研（我们）** |

## 2.7 调研给自研的三条启示

1. **用 MESA-11 定范围基准**，不照抄功能清单。我们 V1 覆盖 5/11 项，其余留 V1.1。
2. **排除清单前置**。5 条红线已写进立项单；每加一个模块先对照红线。
3. **主数据唯一主责系统**。物料/BOM/工艺只能有一个 owner，避免同步冲突。

# 第三部分 · KTG-MES 架构参考

> 定位：**设计参考，不是改造底稿**——本项目已定绿场自研。正确用法是"读设计，不搬代码"。

## 3.1 它是什么

| 项 | 内容 |
|---|---|
| 名称 | 苦糖果 MES（KTG-MES） |
| 定位 | 国内基于 RuoYi 前后端分离版开发的通用开源 MES，面向中小离散制造 |
| 后端仓库 | https://gitee.com/kutangguo/ktg-mes |
| 前端仓库 | https://gitee.com/kutangguo/ktg-mes-ui |
| 许可 | MIT（仓库 LICENSE） |
| 活跃度 | Gitee 5k+ star，镜像仓库最近提交约 11 个月前 |
| 在线体验 | http://www.029tec.com |

本地参考源码：`ktg-mes-reference/backend`（已克隆，只读研究；前端仓库克隆遇 502，未重试）。

## 3.2 技术栈与规模

| 层 | 选型 |
|---|---|
| 后端 | Spring Boot 2.5.0 + Spring Security + MyBatis-Plus 3.4 + Druid |
| 前端 | Vue 2.6 + Element UI 2.15 + ECharts 5 + Axios |
| 中间件 | MySQL 5.7 + Redis 6.2 + RabbitMQ + MinIO |
| 部署 | Docker Compose |

**规模：176 张表**。分布：仓储 64、系统 23、生产 20、质量 16、主数据 14、设备 13、Quartz 11、日历 7、其他 8。

它已不是"轻量 MES"，而是一套完整 ERP-MOM 体系。176 张表对我们 V1 是**反面参照**，不是起点。

## 3.3 值得借鉴的三处设计

### 3.3.1 工单 → 任务 → 报工 → 质检 → 入库 链路

核心表：`pro_workorder`（工单）、`pro_workorder_bom`（用料）、`pro_route_process`（工艺路线）、`pro_task`（任务）、`pro_feedback`（报工）、`qc_ipqc`（制程检验，通过 `source_doc_id` 关联报工）。

**借鉴点**：报工和质检用 `source_doc_id` 做引用式关联，不把检验字段塞进报工表。一条报工可挂多条检验，质检模块能独立演进。

### 3.3.2 报工的"数量四分法"

`pro_feedback` 把报工数量拆成四字段：`quantity_feedback`（报工数）、`quantity_qualified`（合格数）、`quantity_unquanlified`（不合格数）、`quantity_uncheck`（待检数），配合 `is_check` 标志位。

**借鉴点**：过站作业可用这个模型，在 SN 级记录"通过/待检/不合格"，不用引入复杂质检模块。

### 3.3.3 统一待检队列

RuoYi MES 的 `PendingInspect` 用一条 `UNION ALL` 把 6 个来源的待检任务聚合成一个队列。

**借鉴点**："统一入口 + 分类处理"。我们 V1 虽只有过站一个来源，但数据模型要预留 `source_type` 字段。

## 3.4 不能照搬的四处

| 项 | 原因 |
|---|---|
| 176 张表 | 远超 V1 的 4 模块需要，照搬即范围失控 |
| Java + Redis + RabbitMQ + MinIO | 与 Python FastAPI + SQLite 选型冲突，运维成本翻倍 |
| RuoYi 权限体系 | V1 只做单账号登录，不需要 23 张系统表 |
| 触屏端 / PDA / Android | 已写进排除清单 |

## 3.5 与我们 V1 的映射

| 我们的模块 | 对应借鉴 | 简化做法 |
|---|---|---|
| 工单维护 wo | `pro_workorder` + `pro_workorder_bom` | 只保留工单 + 产品 + 计划数 + SN 清单，不做排产 |
| 过站作业 op | `pro_feedback` 四分法 + `is_check` | SN 级记录，站点顺序校验，不做工序任务拆分 |
| 包装出库 pack | WM 出入库链路 | 按配比装箱，不引入 64 张仓储表 |
| 数据查询 query | `source_doc_id` 引用式关联 | 按 SN 正反向追溯，不做全批次谱系 |

## 3.6 状态机设计要点

成熟 MES 工单状态机：`待排产 → 已排产 → 已下发 → 生产中 → 已完工 → 已入库`。

**关键纪律**：状态流转收敛在服务层统一方法里，页面只调方法、不直接改状态。校验规则写在一处，不散落在各页面。我们 V1 的 SN 状态流转也应按此设计。

# 第四部分 · 系统设计

## 4.1 方案总览

| 维度 | 内容 |
|---|---|
| 目标 | 搭建 MES 满足戴盟小批量生产；现状是记录混乱、无生产系统 |
| 路线 | 绿场自研，参照系统仅作规格输入 |
| V1 范围 | 工单 → 过站 → 包装 → 查询四模块闭环 + 单账号登录 |
| 技术 | Vue 3 + FastAPI + SQLite；手机浏览器手动输入 |

方案服务于"小批量生产的可追溯记录"，不是全厂数字化。

## 4.2 四层架构

| 层 | 内容 |
|---|---|
| 接入层 | 手机浏览器 + 账号登录（手动输入 SN；扫码枪后续加） |
| 前端层 | Vue 3 + TypeScript · 工单/过站/包装/查询 |
| 服务层 | Python FastAPI · 状态机校验 / 事务 / 幂等 |
| 数据层 | SQLite 单文件（起步）→ PostgreSQL（多站点时迁移） |

**单机部署**：一个进程 + 一个 SQLite 文件；手机浏览器局域网直连；断电重启数据不丢；配置与数据分离。

### 概念解释（服务层与数据层的四个关键词）

**状态机校验** = 规定 SN 只能按路线走、不能跳站。手机输入 SN 后，系统先检查"这个站是不是序列里的下一站"，不是就拒绝。

**事务** = 要么全做成，要么全当没做。例如 SN 从 A 站转到 B 站要同时改两处记录，绑定成一个事务，中途失败则全部回滚，避免账对不上。

**幂等** = 同一操作点两次，只算一次。手机输入时手抖提交两次，系统认出"这台 SN 这一站已过"，不会重复记一条。

**SQLite → PostgreSQL** = 数据库升级路径，现在不用决策。SQLite 一个文件零安装、断电不丢，适合单机小批量；等真有多站点、多人同时写，再换 PostgreSQL 独立服务，数据结构不用推倒重来。

## 4.3 数据模型：8 张核心表

| 表 | 职责 | 关键设计 |
|---|---|---|
| `products` / `locations` | 产品与产出地点 | 建单下拉数据源 |
| `wos` 工单 | 产品/批次/计划数/站点序列 | 站点按单配置，存 JSON 数组 |
| `wos.sn_list` | 工单下的 SN 清单 | 导入生成，每条带状态 |
| `units` 单元 | SN 当前状态与所在站 | 状态机收敛在服务层 |
| `station_records` 过站记录 | 通过/不良/原因码/时间 | 引用式关联 SN，不塞进单元表 |
| `boxes` / `packs` | 箱号与装箱明细 | 配比建单时填，末站通过才允许 |
| `accounts` | 单账号 admin | V1 只此一条，V1.1 再扩 |

参照系统 11 类实体（作规格输入）：`products` / `locations` / `wos` / `units` / `snBindings` / `boxes` / `accounts` / `qualityLocks` / `lock` / `packCfg` / `packs`。

## 4.4 工单模块

建单字段：产品（6 类）/ 批次 + 计划数 / 产出地点（戴盟 / 联想）。
SN 清单：导入 Excel / TXT，格式 `DAP93226AS00019D`，导入即校验重复。
站点配置：每工单可配顺序，背包单 / 夹爪单各走各的，存为有序数组。
工单状态：草稿 → 已下发 → 生产中 → 已完工 → 关闭。

**开发重点**：SN 导入功能 + 站点按单可配。

## 4.5 过站模块

SN 状态机：`待过站 → 通过 → 不良 → 返修 → 已过站`（返修回当前站重测）。

动作流程：输入 SN → 校验是否在本单站点序列 → 校验顺序合法（不能跳站）→ 判定通过 / 选不良原因码 → 返修后回当前站。

**核心纪律**：状态流转收敛在服务层统一方法，页面只调方法、不直接改状态。

## 4.6 包装模块

配比规则：建单时填 N 台/箱，不写死背包+夹爪，不同产品不同配比。
装箱校验：所有 SN 通过最后一站；未过站 SN 输入即拒绝；满配比自动封箱。
出库记录：生成箱号、记录装箱 SN 清单、封箱时间与操作人。

## 4.7 查询模块

| 查什么 | 返回什么 | 优先级 |
|---|---|---|
| 按 SN 追溯 | 工单 / 过站记录 / 不良返修 / 箱号 | V1 必做 |
| 按工单查进度 | 已过站 / 剩余 / 不良数 | V1 必做 |
| 按箱号查 | 箱内 SN 清单 / 封箱出库时间 | V1 必做 |
| 导出 Excel | 追溯结果导出 | V1.1 延后 |

追溯闭环是验收标准第 1 条——查询模块不是附属功能，是主线终点。

## 4.8 四条技术纪律

1. **状态机收敛服务层**：页面只调方法不直接改状态；校验规则写一处
2. **事务与幂等**：报工/装箱放事务中；接口带幂等键防重复提交
3. **并发乐观锁**：不用原 rev 轮询，重新设计版本号冲突检测
4. **三道质量门禁**：资产在不在 / 能不能打开 / 算得对不对
